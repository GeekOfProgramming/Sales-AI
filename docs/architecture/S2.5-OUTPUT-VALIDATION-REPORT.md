## 1. Executive Summary

SalesAI S2.5 implements a lightweight, deterministic, provider-independent output validation layer for SalesAI's external LLM Gateway. In accordance with the S2.5 architecture specification (`docs/architecture/SALESAI-S2.5-OUTPUT-SCHEMA-VALIDATION-AND-REPAIR.md`):

1. **A syntactically valid JSON response is NOT automatically considered schema-valid, factually grounded, or approved for use.**
2. A typed output validation engine (`LLMOutputValidator` returning `OutputValidationResult`) enforces strict identity, syntax, schema, evidence grounding, opt-out precedence, and security boundaries.
3. A versioned static schema registry (`SchemaRegistry`) defines explicitly typed Pydantic schemas for all seven task families (treating Website Extraction Pass A and Pass B as independent schemas).
4. Local single-fence normalization safely strips whole-response code fences without network calls, while rejecting conversational commentary or multiple objects.
5. Strict syntax parsing detects duplicate keys at any depth, multiple JSON objects, non-object roots, NaN/Infinity, and excessive nesting depth.
6. Local opt-out, refusal, and bounce signals strictly override conflicting positive model classifications, preventing models from converting opt-outs into positive sales leads.
7. Bounded repair policy creates a disabled, single-attempt repair plan with zero network calls, zero provider escalation, and zero tier escalation.
8. Model output is strictly prevented from authorizing email sending, modifying budgets, altering routing, confirming meetings, or mutating operational databases.
9. All output text, personal data, and credentials are completely scrubbed from representations and application logs.

## 4. Architectural Implementation Details

### 4.1 Schema Registry (`sales_engine/llm_gateway/output_schemas.py`)
- Defines `StrictOutputBaseModel` with `extra="forbid"`, `str_strip_whitespace=True`, and strict primitive validation.
- Implements versioned static registry `SchemaRegistry` (`SCHEMA_REGISTRY_VERSION = "1.0.0"`).
- Maps canonical task and subtask combinations to their immutable Pydantic schemas.
- Caller-provided `response_schema` cannot override static task definitions or instantiate arbitrary classes.

### 4.2 Bounded Repair Policy (`sales_engine/llm_gateway/repair_policy.py`)
- Defines `RepairProposal` and `RepairPolicy` (`REPAIR_POLICY_VERSION = "1.0.0"`).
- Separates failure modes:
  - **Formatting / Syntax Errors:** (e.g. missing required field, whole-response fence with trailing comma, extra fields) marked `repairable=True`, `suggested_repair_instruction` provides clean schema prompt.
  - **Semantic / Grounding / Security Errors:** (e.g. fabricated citations, unknown evidence refs, opt-out overrides, prompt injection reflections, identity mismatches) marked `repairable=False`, routed to manual business review.
- Strictly bounds repair attempt count to at most 1 (`prior_attempt_count >= 1` forbids further repair proposals).
- `dispatch_allowed` is hardcoded to `False` in S2.5; execution requires future S2.6 budgeting and authorization. Zero network calls or model escalations occur.
- Suggested repair instructions contain zero customer records, PII, secrets, or raw provider output.

### 4.3 Output Validator Engine (`sales_engine/llm_gateway/output_validation.py`)
- Implements `LLMOutputValidator` and `OutputValidationResult` (`OUTPUT_VALIDATOR_VERSION = "1.0.0"`).
- **Identity & Provenance:** Enforces exact match of `request_id`, canonical `task_id`, `provider`, `model`, and subtask.
- **Strict Syntax Parsing:** Custom JSON decoder detects duplicate keys at any depth, rejects `NaN`/`Infinity`, multiple concatenated objects, non-object roots, and excess depth (>8).
- **Local Normalization:** Single whole-response Markdown code fences are stripped locally (`normalization_applied=True`); conversational commentary preceding or following the fence is strictly rejected.
- **Evidence Reference Grounding:** Verifies every cited reference against locally supplied, approved evidence ID sets; unknown or duplicate references trigger hard validation rejection. Valid references set `needs_business_review=True`.
- **Opt-Out Precedence:** When local opt-out or bounce signals are detected, model classifications proposing positive interest or meeting scheduling are blocked with `OPT_OUT_OVERRIDE_PREVENTED`.
- **Security & Operational Isolation:** Scans for reflected prompt injections and leaked credentials; rejects model outputs attempting to authorize operational actions (`send_email`, `change_budget`, `confirm_meeting`).
- **Safe Representation:** `__repr__`, `__str__`, and `safe_log_dict()` scrub all raw output content, customer PII, and credentials.
- **Async Parity:** `validate_async` provides identical deterministic validation parity with `validate`.

## 7. Remaining Limitations & Blockers for Live Deployment

1. **No Real Network Calls or API Keys Active:** All S2.5 components operate purely offline with zero network dispatch. Real HTTPS invocation requires S2.6 authorization and S3 benchmarking.
2. **Operational Call Sites Unmigrated:** The six live SalesAI LLM call sites remain untouched on their existing local clients. Migration belongs to Stage S2.7.
3. **Repair Dispatch Disabled:** Repair proposals generated in S2.5 are strictly informational and non-actionable (`dispatch_allowed=False`). Authorization and budget checks will be implemented in S2.6.
4. **Operator Authentication Non-Authenticating:** Operator tokens and approval metadata remain unauthenticated placeholders until S2.6 implements actual authentication.
5. **Human Review Gate Required:** Valid schema output citing evidence references requires downstream business grounding review before outreach drafts or suggestions can be approved.
