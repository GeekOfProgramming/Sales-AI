## 1. Executive Summary

SalesAI S2.3.1 resolves critical validation and state hardening defects identified in the S2.3 v2 sequential evaluation and routing engine. Under the S2.3 v2 baseline, benchmark scorecards could approve arbitrary or mismatched candidates, terminal states accepted replay submissions, production routes accepted forged provider/model attributes or unauthenticated operator approvals, and unverified model IDs with outdated 2024–25 pricing were hardcoded as defaults.

S2.3.1 introduces strict fail-closed integrity validation across all evaluation and routing boundaries:
1. **Scorecard Validation (B1):** Rejects any scorecard whose candidate ID, canonical task, subtask, or tier does not match the candidate currently scheduled for evaluation. Rejects unsimulated scorecards targeting disabled candidate slots.
2. **Production Route Hardening (B2):** Enforces that all registered routes possess authenticated operator provenance (`approved_by`), an approved policy status, and match the catalog candidate's exact provider, model, tier, task allowance, and enabled status. Guards against post-approval catalog mutations or candidate disablement.
3. **Replay and Terminal State Protection (B3):** Prevents mutation of evaluation history in terminal states (`approved`, `unresolved`) and during paused evaluation (`tier_exhausted`). Rejects duplicate and out-of-order scorecards with zero state mutation. Requires an authenticated operator token and distinct run ID for explicit re-evaluation.
4. **Neutral Candidate Slots & Null Pricing (B4):** Replaces vendor-dated model IDs with 16 neutral slot identifiers (`t1_c1`..`t4_c4`). Treats pricing and capabilities as unknown (`None`/`null`) until separately verified from providers with documented provenance.
5. **Immutability & Subtask Isolation (B5):** Freezes `ModelCandidate` and `PricingMetadata` records. Strictly isolates `website_extraction` Pass A and Pass B evaluation states. Rejects duplicate `(tier, priority)` slot registration and validates task priority overrides.

## 2. Defects Remediated (B1–B5 Analysis)

### B1 — Untrusted / Mismatched Scorecards Approving Arbitrary Candidates
* **Vulnerability in S2.3 v2:** `EvaluationPlanner.process_scorecard` only verified canonical task matching. A scorecard targeting a fabricated candidate ID, a different tier (e.g. Tier 4 during Tier 1 evaluation), or a different subtask (e.g. `pass_b` for a `pass_a` state) was accepted and stamped into `state.approved_candidate_id`.
* **Correction in S2.3.1:** Pre-validation verifies active `evaluating` state, canonical task key, exact subtask key (`validate_subtask_id`), scheduled candidate ID match (`scorecard.candidate_id == current_candidate.candidate_id`), scorecard tier match (`scorecard.tier == state.current_tier == current_candidate.tier`), candidate task authorization, and availability/simulation flags before modifying `state.history`. Any mismatch raises typed `LLMEvaluationIntegrityError` with zero state/history mutation.

### B2 — Router Returning Forged Provider, Model, or Tier as Approved
* **Vulnerability in S2.3 v2:** `TaskRouter.set_approved_route` only checked that `decision.candidate_id` existed in the catalog. It did not cross-check provider, exact model, tier, task eligibility, enablement, or operator provenance. Additionally, `resolve_approved` did not detect post-approval catalog mutations.
* **Correction in S2.3.1:** Both registration and resolution strictly validate:
  - Non-empty operator authority (`decision.approved_by`).
  - Active candidate enablement in catalog.
  - Task eligibility (`candidate.is_task_allowed(canonical)`).
  - Exact match of `provider_id`, `model`, and `tier` between decision and catalog candidate.
  - Re-verification during `resolve_approved` to guard against catalog drift or disablement after approval.

### B3 — Terminal States Accepting Replay / Stale Results
* **Vulnerability in S2.3 v2:** Scorecards could be re-submitted repeatedly after approval, expanding history and returning repeated approvals. Scorecards submitted while in `tier_exhausted` or `unresolved` were also accepted.
* **Correction in S2.3.1:** Rejects scorecards when state is not in `evaluating`. Rejects duplicate scorecards for candidates already present in state history. Provides `reset_evaluation(state, operator_token, new_run_id)` requiring explicit operator authorization and a fresh run ID to reset terminal states.

### B4 — Fake/Unverified Model IDs, Pricing, and Capabilities
* **Vulnerability in S2.3 v2:** Default catalog contained concrete dated vendor SKUs, asserted generic capabilities, and included 2024–25 token prices without proof of current availability.
* **Correction in S2.3.1:** All 16 default candidate slots are migrated to neutral IDs (`t1_c1`..`t4_c4`) across the four tiers (Budget, Balanced, High Fidelity, Flagship). All slots default to disabled, with provider set to `unassigned`, exact model to `unverified_slot`, capabilities empty, and pricing `None`/`null`. Backward compatibility is preserved via internal alias mapping (`catalog.candidate_aliases`).

### B5 — Mutability, Subtask Isolation, and Eligibility Guards
* **Vulnerability in S2.3 v2:** `ModelCandidate` was mutable via attribute assignment. Duplicate `(tier, priority)` slots could be registered. `website_extraction` subtasks were not strictly validated.
* **Correction in S2.3.1:** `ModelCandidate` and `PricingMetadata` are frozen Pydantic models (`frozen=True`, `extra="forbid"`). `ModelCatalog` enforces slot collision checks on `(tier, priority)` and validates task priority overrides. Strict subtask taxonomy enforces `pass_a`/`pass_b` isolation for website extraction and forbids subtasks on all other tasks.
