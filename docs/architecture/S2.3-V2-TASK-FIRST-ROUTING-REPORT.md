## 1. Executive Summary & Policy Implementation

Milestone S2.3 v2 establishes the task-first, Tier-1-first sequential model evaluation state machine and production routing architecture for SalesAI.

### 1.1 Core Selection & Routing Principles
1. **Tier-1-First Default:** All six active SalesAI LLM task families (`website_extraction`, `job_analysis`, `discovery_query_generation`, `inbox_classification`, `reply_suggestion`, `outreach_draft`) strictly default to **Tier 1 (Budget)**.
2. **Sequential One-at-a-Time Evaluation:** Candidates within a tier are evaluated sequentially (slots 1..4). If candidate #1 satisfies acceptance criteria, evaluation halts immediately and records it as approved; the remaining 15 candidate slots across all tiers are never tested.
3. **Independent Per-Task Resolution:** Model selection is completely independent per task. Different tasks may select different providers and models within Tier 1 or across tiers without coupling.
4. **Strict Safety Gating:** Safety-critical benchmark failures (e.g., unsubscribes misclassified as referrals, fabricated team capacity, prompt injection leaks) strictly block approval regardless of high general performance scores.
5. **Tier Exhaustion & Explicit Operator Promotion:** Only after all eligible candidates in a tier fail is the tier marked `TIER_EXHAUSTED`. Elevation to the next tier strictly requires explicit operator approval (`promote_tier(operator_approval=True)`).
6. **Production Isolation:** Normal production inference uses exclusively previously approved models. A runtime failure or malformed response **never** silently invokes alternative paid models or escalates tiers.
7. **Offline Scaffolding (Zero Cost):** S2.3 v2 operates purely offline with mocked scorecards; zero commercial API calls are executed and zero credit costs are incurred.

## 3. Demonstration of Mandatory Dry-Run Examples

The test suite in `tests/test_s2_3_sequential_task_routing.py` deterministically verifies the five mandatory dry-run workflows specified in Section 7 of the specification:

### Example A: Candidate Rotation & Early Stop
- **Task:** `website_extraction`
- **Workflow:** Tier 1 Candidate #1 (`t1_c1_openai_mini`) fails source grounding (score 0.40) -> Planner transitions to `PROPOSE_NEXT_IN_SAME_TIER` -> Tier 1 Candidate #2 (`t1_c2_anthropic_haiku`) passes all criteria (score 0.95) -> Planner returns `ACCEPT_CANDIDATE` and approves candidate #2.
- **Verification:** Testing immediately stops for `website_extraction`. `inbox_classification` remains completely unmutated and unselected. Remaining 14 candidate slots are never touched.

### Example B: Tier Exhaustion & Explicit Operator Promotion
- **Task:** `inbox_classification`
- **Workflow:** All four Tier 1 candidates fail intent classification (unsubscribes conflated with referrals) -> Planner returns `TIER_EXHAUSTED_REQUIRES_APPROVAL` and enters status `"tier_exhausted"`.
- **Verification:** Before operator approval, candidate resolution returns `None` (zero automated cost). Following simulated operator approval (`promote_tier(operator_approval=True)`), the planner transitions to Tier 2 and suggests Candidate #1 (`t2_c1_openai_standard`). Zero live API calls are executed.

### Example C: Safety-Critical Failure Forbids Pass
- **Task:** `outreach_draft`
- **Workflow:** Tier 1 Candidate #1 generates well-structured, fluent JSON (score 0.88), but invents a company team size commitment (`safety_critical_passed=False`).
- **Verification:** Planner rejects approval and transitions to `PROPOSE_NEXT_IN_SAME_TIER`, proposing Candidate #2 (`t1_c2_anthropic_haiku`). No email is generated or dispatched.

### Example D: Early-Stop Optimization & Vendor Diversity
- **Task:** `job_analysis` vs `discovery_query_generation`
- **Workflow:** `job_analysis` Tier 1 Candidate #1 (`t1_c1_openai_mini`) passes on its first evaluation -> Accepted immediately; only 1 candidate tested out of 16.
- **Verification:** Simultaneously, `discovery_query_generation` independently configures a different vendor priority override (`t1_c2_anthropic_haiku`), proving tasks independently select vendors without global coupling.

### Example E: Fail-Closed Behavior on Unconfigured Models
- **Task:** `website_extraction`
- **Workflow:** With an unconfigured or empty catalog, `TaskRouter.resolve_approved()` raises `LLMNotConfiguredError`.
- **Verification:** System fails closed cleanly without falling back to local Ollama or fabricating model selections.
