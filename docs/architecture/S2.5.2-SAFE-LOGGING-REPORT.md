## 1. Executive Summary

SalesAI S2.5.2 resolves a sensitive-data logging defect discovered during independent review of S2.5.1 (`docs/architecture/SALESAI-S2.5.2-SAFE-LOGGING-AND-PROVIDER-METADATA-HARDENING.md`). 

Previously, `provider_request_id` from upstream provider headers (`x-request-id`) or response bodies (`id`) was directly included in `LLMResponse.safe_log_dict()`, copied into `OutputValidationResult.metrics`, and emitted via `OutputValidationResult.safe_log_dict()`. If an untrusted upstream returned a value containing sensitive data (such as an email address `private_person@example.invalid`, bearer token, or API key), the value leaked into structured log dictionaries despite the safe-logging contract.

S2.5.2 hardens the logging layer to treat all upstream correlation identifiers, response headers, and raw metadata as untrusted:
1. **B1 (Untrusted Upstream Correlation Identifier):** Raw `provider_request_id` and `raw_metadata` are preserved solely in restricted in-memory transport objects. They are never emitted through `safe_log_dict()`, `__str__`, `__repr__`, exceptions, or audit logs. In safe logs, `has_provider_request_id: bool` and `provider_request_id: null` are emitted.
2. **B2 (Closed Metrics Allowlist):** `OutputValidationResult.safe_log_dict()` enforces an explicit, shallow allowlist of known scalar measured fields (`input_tokens`, `output_tokens`, `latency_ms`, `cost_usd`, `has_provider_request_id`, `provider_request_id: null`). Un-allowlisted keys (e.g. `private_notes`), nested dictionaries, and raw headers are discarded at the logging boundary. Unmeasured costs remain `None` and are never converted to zero.
3. **B3 (Uniform Safe Logging Across Gateway):** Standardized `sanitize_log_str()` redacts emails, API tokens/secrets (`sk-`, `bearer`, `ghp_`), filesystem paths, and control characters across `LLMRequest`, `LLMResponse`, `OutputValidationResult`, `RepairProposal`, `OpenAIProvider`, and `LLMError`. Network/JSON decode exceptions do not leak raw exception text.
4. **B4 (Identity Preservation Without Disclosure):** In-memory request/response routing and validation integrity logic retain exact strings to perform strict verification without alteration. Redaction and sanitization occur strictly at the logging/repr boundary.
5. **B5 (Adversarial Offline Verification):** 18 new deterministic offline tests cover email in `x-request-id`, bearer tokens, `sk-` keys, Windows paths, multiline/control characters, nested metrics, cookies in `raw_metadata`, malicious model labels, and sync/async parity.
6. **B6 (Residual Limitations):** Automated sanitizers do not guarantee semantic PII detection in free text; cryptographic operator session validation remains a prerequisite for S2.7 and live API activation.

## 2. Defect Reproduction & Resolution (Before vs. After)

### Defect B1 / B2 Reproduction
```python
# Upstream response returned with injected sensitive correlation ID:
resp = LLMResponse(
    request_id="req-123",
    task_id="inbox_classification",
    provider="google",
    model="gemini-2.5-flash",
    content='{"category": "question", "confidence": 0.9}',
    provider_request_id="private_person@example.invalid",
)
res = validator.validate(req, resp)
```

| Component / Output | Before S2.5.2 | After S2.5.2 Hardening |
|:---|:---|:---|
| `resp.safe_log_dict()["provider_request_id"]` | `"private_person@example.invalid"` ❌ | `None` (plus `has_provider_request_id: True`) ✅ |
| `res.safe_log_dict()["metrics"]["provider_request_id"]` | `"private_person@example.invalid"` ❌ | `None` (plus `has_provider_request_id: True`) ✅ |
| `repr(resp)` / `str(resp)` | Excluded raw content but risk of leaking injected headers ⚠️ | Strict `sanitize_log_str()` on all fields; `has_provider_request_id: True` ✅ |
| `res.safe_log_dict()["metrics"]["private_notes"]` | Permissively copied entire dictionary ❌ | Stripped by closed metrics allowlist ✅ |
| Upstream `raw_metadata` with cookies | Available to log consumers ⚠️ | Never emitted in any `safe_log_dict()` or `repr` ✅ |
| `LLMError` string representation | Echoed raw provider / task / message ⚠️ | All fields sanitized via `sanitize_log_str()` ✅ |

## 6. Security and Architectural Invariants Maintained

1. **In-Memory Transport Integrity Preserved:** In-memory objects (`LLMResponse.provider_request_id`, `LLMResponse.raw_metadata`, `LLMRequest.model`) retain unredacted values so downstream validation, routing matching, and transport correlation operate without breakage.
2. **Zero Log Leakage:** Structured log dictionaries and string representations strictly filter sensitive patterns (emails, tokens, secrets, filesystem paths, control characters).
3. **Zero Operational Authority for LLM Outputs:** LLM outputs cannot send emails, confirm appointments, alter budgets, or mutate database state.
4. **Deterministic Offline Execution:** All Gateway validation tests execute completely offline without network IO, API tokens, or model downloads.
5. **No Automatic Retries or Escalation:** Validation failures do not trigger retries or tier escalation.

---

## 7. Remaining Limitations & Boundaries Before S2.6

- **No Live API Dispatch:** Gateway remains disabled by default (`LLM_GATEWAY_ENABLED=false`).
- **Offline Repair Proposals Only:** Repair proposals remain purely advisory plans (`dispatch_allowed=False`). Live repair execution requires S2.6 budget, retry, and concurrency controls.
- **Operator Session Authentication:** `approved_by` operator tokens are structural identity markers; cryptographic session authentication is deferred to S2.7.
