## 1. Executive Summary

SalesAI S2.4 introduces a deterministic, privacy-preserving payload construction and untrusted-content isolation layer between SalesAI's local data repository (company database, raw Excel files, contact directories, and email inbox history) and external LLM APIs.

In accordance with laptop-first privacy principles:
- **Zero Full Records Outbound:** Full company databases, entire email threads, raw workbook tables, address books, and session secrets remain strictly on the developer's laptop.
- **Minimum Task Evidence:** Only explicitly allowlisted, task-specific, bounded, and sanitized text excerpts are prepared for outbound model requests.
- **Deterministic Redaction:** Detects and masks personal email addresses, phone numbers (Italian and international formats), IBANs, payment cards (verified with Luhn algorithm), bearer tokens, API keys, credentials, local absolute file paths, and session cookies. Innocuous numeric BIM standards (`ISO 19650`, `UNI 11337`, `DIN 276`, `BS 1192`, `IFC 4.3`, `LOD 300`, etc.) are preserved intact.
- **Untrusted-Content Isolation:** All website text, job descriptions, inbound email bodies, and search snippets are isolated inside JSON-escaped data envelopes within user prompts. They are never promoted to system instruction roles and cannot override model tier, provider, routing, budget ceiling, or sending permissions.
- **Full-Text Pre-Truncation Inbound Email Safety:** All inbound email text is scanned locally for opt-out, refusal, unsubscribe, and bounce signals against the complete original body **before** any character trimming or redaction. If an unsubscribe phrase is present (even at the end of a long message), it triggers manual review and suppression flags rather than being discarded by context truncation.
- **Zero Provider Dispatch:** The payload builder constructs typed `LLMRequest` objects without making network requests, accessing paid APIs, or modifying the six operational LLM call sites.

## 2. Architecture & Components Implemented

Five self-contained, lightweight components were created or extended in `sales_engine/llm_gateway/`:

1. **`sales_engine/llm_gateway/privacy_filter.py`**:
   - `PrivacyFilter`: Deterministic rule- and regex-based privacy scrubber. Maintains per-request placeholder numbering (e.g. `[PERSONAL_EMAIL_1]`, `[PHONE_1]`, `[IBAN_1]`, `[SECRET_1]`, `[CARD_1]`, `[LOCAL_PATH_1]`). Identical values within a single request map to the same placeholder.
   - `is_luhn_valid`: Validates 13–19 digit payment card numbers with standard Luhn checksum algorithm, avoiding false positives on arbitrary numbers.
   - `RedactionResult`: Safe model tracking sanitized text, redaction counts, manual review flags, and local-only placeholder mapping. Safe `safe_log_dict()`, `__repr__()`, and `__str__()` scrub raw prompts and sensitive values.

2. **`sales_engine/llm_gateway/source_boundaries.py`**:
   - `InputTrustClass`: Enumerates trust hierarchy (`TRUSTED_POLICY`, `APPROVED_BUSINESS_FACTS`, `UNTRUSTED_SOURCE`, `RESTRICTED_LOCAL_ONLY`).
   - `normalize_company_domain`: Normalizes company domains and URLs to clean lowercase hostnames (RFC 1123 compliant), stripping query parameters, auth tokens, ports, paths, and fragments. Rejects data URLs and invalid schemes.
   - `wrap_untrusted_source`: Encodes external content into JSON data objects inside `<UNTRUSTED_CONTENT>` containers. Delimiter tags (e.g. `</UNTRUSTED_CONTENT>`) inside the text are safely JSON-escaped and cannot break out of the container. Fails closed on null bytes and control characters.
   - `contains_prompt_injection`: Detects common prompt-injection phrases for telemetry and auditing.

3. **`sales_engine/llm_gateway/payload_builder.py`**:
   - `PayloadBuilder`: Task-aware payload assembly engine enforcing strict allowlists, bounded character lengths, and trusted system prompts across all six SalesAI task families.
   - `check_full_text_opt_out_signals`: Deterministic full-text scan checking against unsubscribe and bounce regexes before truncation.
   - `PayloadBuildResult`: Complete result contract including `LLMRequest`, included source IDs, redaction counts, omitted fields, policy version (`1.0.0`), and safety flags.
   - `preview_sanitized_payload`: Explicit opt-in local preview utility for authenticated operators, never exposing raw secrets or original PII.

4. **`sales_engine/llm_gateway/errors.py`**:
   - Extended with typed exceptions: `LLMPrivacyError`, `LLMUntrustedContentError`, `LLMAllowlistViolationError`, and `LLMPrivacyRejectionError`.

5. **`tests/test_s2_4_privacy_payload.py`**:
   - 39 offline adversarial test cases using purely synthetic/fictional records.

## 4. Deterministic Redaction & Privacy Transformations

- **Email Addresses:** Standard RFC 5322 email patterns masked to `[PERSONAL_EMAIL_1]`, `[PERSONAL_EMAIL_2]`, etc.
- **Phone Numbers:** Italian landline (`0...`) and mobile (`3...`) numbers, as well as international formats (`+...`), masked to `[PHONE_1]`, `[PHONE_2]`, etc. Word boundaries prevent accidental matching within Italian words (e.g. "coordinatore", "centralino").
- **IBANs:** Italian (`IT...`) and international standard IBANs masked to `[IBAN_1]`, `[IBAN_2]`.
- **Payment Cards:** Numbers between 13 and 19 digits are verified using the Luhn algorithm before masking to `[CARD_1]`. Non-card numbers are preserved.
- **Credentials & API Keys:** Bearer tokens (`bearer ...`), OpenAI keys (`sk-...`), password assignments (`password=...`), client secrets, and environment variable secrets are masked to `[SECRET_1]`, `[SECRET_2]`. Lookahead assertions prevent cascading regex corruption of already-masked tokens.
- **Local Filesystem Paths:** Windows absolute paths (`C:\Users\...`, `C:\Sales-AI\...`) and Unix paths (`/home/...`) masked to `[LOCAL_PATH_1]`.
- **Cookies & Session Tokens:** Session cookies (`sessionid=...`, `connect.sid=...`) masked.
- **Preserved BIM Standards:** Innocent BIM codes (`ISO 19650`, `UNI 11337`, `DIN 276`, `BS 1192`, `IFC 4.3`, `LOD 300`, `Revit 2024`, etc.) and area dimensions (`2500 m2`) are explicitly safeguarded and never modified.

## 5. Untrusted-Content Isolation & Delimiter Defense

Source text is serialized inside typed envelopes:
```xml
<UNTRUSTED_CONTENT source_kind="website_evidence" source_id="src_web_01" untrusted="true">
{"source_id": "src_web_01", "source_kind": "website_evidence", "untrusted": true, "content": "..."}
</UNTRUSTED_CONTENT>
```
1. **JSON Escaping:** Because the source text is serialized as JSON string data, spoofed closing tags (e.g. `</UNTRUSTED_CONTENT>`), markdown headers (`### System:`), or prompt-injection phrases remain inert data values within a JSON structure.
2. **System Prompt Separation:** The system prompt consists solely of static, locally authored instructions (`trusted_policy`). No external or untrusted text is ever concatenated into system prompts.
3. **Control Invariance:** Text inside `UNTRUSTED_CONTENT` cannot supply routing directives, change model tiers, override budgets, or trigger email dispatch.

## 6. Pre-Truncation Inbound Email Safety Invariant

Under traditional context-trimming, a long inbound email (e.g., 7,500 characters) truncated to a 4,000-character budget risks dropping refusal, opt-out, or unsubscribe instructions placed in postscripts or signature footers.

In S2.4:
- The full original text is evaluated locally against `_UNSUBSCRIBE_PHRASES` and bounce patterns **before** any character slicing.
- If an unsubscribe phrase or refusal is detected anywhere in the message:
  1. `is_opt_out_detected = True` is recorded on `PayloadBuildResult`.
  2. `manual_review_required = True` is set.
  3. A deterministic safety notice `[LOCAL SAFETY NOTE: Unsubscribe or refusal signal detected in full local email.]` is attached to the prompt context.
  4. Truncation never causes the opt-out signal to be lost or ignored.

## 7. Operator Authorization Security Requirement (Recording, Not Faking)

> [!IMPORTANT]
> **BLOCKING SECURITY REQUIREMENT FOR S2.7 & PRODUCTION ACTIVATION:**
> Independent security review in S2.3.1 established that `TaskRouter.set_approved_route` validates only that `approved_by` is a non-empty string, and `EvaluationPlanner.reset_evaluation` checks only that `operator_token` is a non-empty string.
> 
> **These are provenance placeholders, NOT authenticated identities.**
> 
> S2.4 confirms that untrusted inputs cannot supply `approved_by` or `operator_token` (such attempts are rejected with `LLMAllowlistViolationError`). However, true cryptographically verified operator authentication (local session tokens, OS-level credential binding, or signed audit logs) remains an unfulfilled requirement. It must be implemented and verified before live external LLM routing or production deployment is enabled. S2.4 does not claim this is resolved.

## 8. Limitations and Non-Claims

1. **Regex Redaction is Technical Minimization, Not a Legal Guarantee:** Deterministic regex pattern matching reduces risk and removes standard identifiers. It cannot guarantee detection of all personal names, esoteric secrets, or ambiguous natural language references.
2. **Conservative Manual Review:** When high-entropy unredacted secrets or fatal control characters are detected, the payload builder marks `manual_review_required = True` and sets `llm_request = None`, performing zero external calls.
3. **No ML / Heavy Wheel Dependencies:** S2.4 uses pure Python standard library and existing Pydantic models. No transformers, spaCy, PyTorch, Ollama, or ChromaDB dependencies were added.
4. **Operational Isolation Maintained:** The six legacy operational LLM call sites and transitional clients remain untouched and disconnected from the Gateway in S2.4.
