## 1. Phase 1 — OpenRouter Billing Classification & Safety Corrections

### 1.1 Policy Mismatch Identification
In S3.5.3B, `classify_model_billing("openrouter", model_id)` contained:
```python
if pid == "openrouter":
    if mid.endswith(":free"):
        return "VERIFIED_FREE_TIER"
    return "VERIFIED_PAID"
```
This marked any model identifier ending in `:free` as `VERIFIED_FREE_TIER`, conflicting with the declared architecture policy that free-tier status requires exact membership in an explicitly approved allowlist.

### 1.2 Implemented Allowlist Classification
In [sales_engine/benchmark/provider_catalog.py](file:///C:/Sales-AI/SalesAI/sales_engine/benchmark/provider_catalog.py), `classify_model_billing` was hardened:
```python
if pid == "openrouter":
    # Only explicitly approved allowlisted models qualify for VERIFIED_FREE_TIER.
    # Unknown :free models must be rejected as UNKNOWN, not VERIFIED_FREE_TIER.
    # Models lacking the :free suffix are VERIFIED_PAID.
    if mid in EXPLICIT_VERIFIED_FREE_MODELS.get("openrouter", set()):
        if mid.endswith(":free"):
            return "VERIFIED_FREE_TIER"
        return "VERIFIED_PAID"
    if mid.endswith(":free"):
        return "UNKNOWN"
    return "VERIFIED_PAID"
```

### 2.2 Root-Cause Diagnostic Analysis & Uncertainty Correction
The S3.5.3B report asserted that the failure was definitively caused by "upstream shared-pool queue saturation." 

**Corrected Finding:**  
The recorded response payload contained only generic error message text: `[RATE_LIMIT] Openrouter rate limit exceeded (HTTP 429)`. OpenRouter's edge gateway did not return error metadata or provider error codes indicating whether the 429 stemmed from:
1. Per-minute burst rate limits (e.g. 20 RPM on free tier).
2. Shared upstream GPU pool congestion.
3. Account-level free tier daily quota exhaustion.
4. Edge proxy throttling.

While upstream pool saturation is a common operational characteristic of public free models, asserting it as the definitive cause without recorded evidentiary proof was inaccurate.

### 2.3 Modular Rate Limit Classification Engine
Created [sales_engine/llm_gateway/rate_limit_diagnostics.py](file:///C:/Sales-AI/SalesAI/sales_engine/llm_gateway/rate_limit_diagnostics.py):
- **`RateLimitDiagnostic` Dataclass:** Captures `cause_category`, `retry_after_seconds`, `provider_error_code`, `provider_error_type`, `safe_diagnostic_message`, and `definitive_cause_proven`.
- **Classification Categories:**
  - `ACCOUNT_QUOTA`: Triggered when error code/message explicitly indicates quota, balance, or billing credit exhaustion. Raises `LLMQuotaExceededError`.
  - `REQUEST_RATE_LIMIT`: Triggered when error code/message explicitly references RPM, TPM, per-minute, or per-day limits.
  - `UPSTREAM_CAPACITY`: Triggered ONLY when provider code/message explicitly references upstream capacity, shared-pool queues, or provider overload.
  - `UNKNOWN_RATE_LIMIT`: Assigned when a generic 429 is received without definitive explanatory metadata (`definitive_cause_proven=False`).
- **Header Parsing:** Safely parses `Retry-After` (and `x-ratelimit-reset`) headers into sanitized numeric seconds.
- **Privacy Guarantee:** Strips all tokens, credentials, and user prompts from diagnostic logs.

### 2.4 Model Evaluation State Correction
In [sales_engine/benchmark/external_runner.py](file:///C:/Sales-AI/SalesAI/sales_engine/benchmark/external_runner.py), `CandidateTaskSummary` was updated with `evaluation_state`:
- When all cases fail due to rate limits before text generation, `evaluation_state` is set to `"INFERENCE_UNVERIFIED / RATE_LIMITED"`.
- Transport-layer rate limits are **not** counted as model safety violations (`safety_violations_count = 0`).
- Disqualification reason is recorded as:  
  `"Inference unverified: Candidate experienced rate limit (HTTP 429) across all cases. No output evaluated (not a model quality or safety assessment failure)."`
