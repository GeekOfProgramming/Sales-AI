## Executive Summary

SalesAI S3.0 establishes an independent, offline-first external LLM benchmark runner and enforces strict paid-dispatch safety gates across all seven canonical LLM Gateway task/subtask paths before any modifications are introduced to SalesAI's six operational call sites.

Two confirmed paid-dispatch accounting blockers identified during S2.6 review (A1 duplicate request dispatch and A2 pricing/candidate mismatch) have been resolved and verified with deterministic regression tests before allowing benchmark execution. The benchmark system operates 100% offline in dry-run mode using synthetic fixtures and deterministic mock providers, with live commercial API execution strictly locked behind operator authorization gates.

## 1. Mandatory First Fixes: Paid-Dispatch Safety Gates

### A1 — Duplicate Network Dispatch & Idempotency Hardening
- **Vulnerability:** Calling `RuntimeGuard.guarded_call` twice with the same `request_id` previously dispatched the upstream provider twice while reusing a single reconciled ledger reservation.
- **Root Cause:** The guard did not track in-flight or completed request responses in runtime memory and allowed re-entry when a ledger reservation was already `RECONCILED`.
- **Resolution:**
  1. `RuntimeGuard` maintains `_response_cache` to return safely cached prior responses if an identical `request_id` is re-submitted serially, preventing secondary network dispatches.
  2. `_in_flight_request_ids` tracks active invocations, raising `LLMDuplicateRequestError` on concurrent attempts.
  3. `BudgetLedger.reserve()` checks existing records: if a reservation is already `RECONCILED`, `UNCERTAIN`, or `CANCELLED`, it strictly rejects duplicate reservation with `LLMDuplicateRequestError`, protecting across process restarts.
- **Verification:** Verified by `test_a1_serial_duplicate_returns_cached_response_single_dispatch`, `test_a1_concurrent_duplicate_raises_duplicate_error`, and `test_a1_restart_db_duplicate_raises_duplicate_error`.

### A2 — Pricing & Candidate Identity Binding
- **Vulnerability:** Budget reservations could be established under an inexpensive candidate while the caller dispatched an expensive model.
- **Root Cause:** `RuntimeGuard` and `LLMProviderGateway` did not enforce strict multi-field identity equality between the request attributes and the candidate binding.
- **Resolution:**
  1. Implemented `_validate_candidate_binding` asserting exact string equality for `request.provider == candidate.provider_id`, `request.model == candidate.exact_model_id`, and `request.tier == candidate.tier`.
  2. Added preflight assertion in `RuntimeGuard.guarded_call` before ledger preflight and immediately prior to provider invocation.
  3. In `LLMProviderGateway.generate()`, enforced route decision binding unless explicitly authorized under benchmark mode (`is_benchmark=True`), where candidate binding is still strictly checked.
  4. Mismatches raise `LLMCandidateMismatchError` with zero HTTP dispatch and zero budget reservation.
- **Verification:** Verified by `test_a2_mismatched_candidate_model_fails_closed_before_dispatch` and `test_a2_mismatched_provider_or_tier_fails_closed`.

## 2. Benchmark Architecture & Components

### 2.1 Benchmark Runner (`sales_engine/benchmark/external_runner.py`)
- **Offline-First Execution:** Default `--dry-run` mode uses `MockBenchmarkProvider`, performing 100% deterministic local evaluations with zero external network access.
- **Strict Paid Gate:** Attempting `--live` execution immediately raises `LLMNotConfiguredError`, refusing unapproved live commercial dispatches.
- **Architecture Reuse:** Leverages existing production infrastructure: `LLMProviderGateway`, `RuntimeGuard`, `BudgetLedger`, `ProviderRegistry`, and `LLMOutputValidator`.
- **Sequential Tier 1 Evaluation:** Tests Tier 1 Candidate #1 first (`t1_c1`); if candidate qualifies (100% safety pass rate and overall pass rate >= 80%), stops evaluation for that task. If #1 fails, proceeds to #2..#4.
- **Isolated Evaluator Data:** Expected answers, gold labels, and evaluator checks are strictly separated from prompts and never exposed to the model under test.

### 2.2 Golden 10 Dataset Mapping (`sales_engine/benchmark/golden_mapper.py`)
- Mapped 9 compatible scenarios from `docs/architecture/SalesAI_Golden_10_Synthetic_v1.json` to canonical Gateway schemas:
  - `company_extraction` -> `website_extraction:pass_a`
  - `company_qualification` -> `job_analysis`
  - `email_draft` -> `outreach_draft`
  - `reply_classification` -> `inbox_classification`
- **Flagged Unmappable Case:** `G05` (`meeting_time_extraction`) is explicitly flagged as unmappable because extraction of calendar meeting times has no corresponding Gateway task contract.

### 2.3 Comprehensive 70-Case Synthetic Catalog (`sales_engine/benchmark/fixtures_s3.py`)
- Covers all 7 canonical Gateway task/subtask paths (10 cases per path: 5 grounded, 5 adversarial):
  1. `website_extraction:pass_a` (10 cases)
  2. `website_extraction:pass_b` (10 cases)
  3. `job_analysis` (10 cases)
  4. `discovery_query_generation` (10 cases)
  5. `inbox_classification` (10 cases)
  6. `reply_suggestion` (10 cases)
  7. `outreach_draft` (10 cases)
- Adversarial fixtures evaluate conflicting evidence, prompt injection resilience, opt-out honor, and hallucination resistance.

### 2.4 Multi-Format Reporting (`sales_engine/benchmark/report_s3.py`)
- Generates three synchronized local reports:
  - `benchmark_results_{run_id}.json`: Complete execution run metadata and safe diagnostic logs.
  - `benchmark_cases_{run_id}.csv`: Flattened tabular rows (one row per candidate x task x case).
  - `BENCHMARK_REPORT_{run_id}.md`: Human-readable markdown summary with qualification scorecard.
- **Operator Authority Boundary:** Reports explicitly document that candidate recommendations are **proposals only** and do NOT constitute production route approvals.

### 2.5 Local CLI Runner (`scripts/benchmark_external_llm.py`)
- Provides CLI control with flags:
  - `--dry-run` (default True, safe offline mode)
  - `--live` (strictly fails closed in S3.0)
  - `--task` (filter to specific task or "all")
  - `--candidate` (evaluate specific candidate or Tier 1 sequence)
  - `--max-cases` (cap cases per task for rapid smoke testing)
  - `--output-dir` (target directory for reports)
  - `--format` (`all`, `json`, `csv`, `markdown`)
