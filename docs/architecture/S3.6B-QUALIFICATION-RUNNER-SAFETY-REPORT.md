## 2. Phase 1 — Invalid Task Selection Hardening (Fail-Closed)

### 2.1 The Vulnerability in Prior Implementation
Previously, `external_runner.py` resolved target paths using:
```python
target_paths = filtered_paths or all_task_paths
```
If an operator passed a misspelled task name (e.g. `--task website_extracshun:pass_a`), `filtered_paths` evaluated to an empty list `[]`, causing the runner to silently fall back to `all_task_paths`, unintentionally initiating a 70-case full benchmark run.

### 2.2 Hardened Implementation
In `sales_engine/benchmark/external_runner.py`:
1. **Validation Order:** Task filter validation is executed immediately at entry of `run_benchmark()`, *before* any live candidate configuration, budget reservations, or credential checks.
2. **Rejection of Unknown Tasks:** An unknown or misspelled task raises `LLMNotConfiguredError` with `INVALID_TASK_FILTER`.
3. **Rejection of Blank/Whitespace:** Whitespace or empty filter strings raise `LLMNotConfiguredError`.
4. **Rejection of Ambiguous Tasks in Live Mode:** In live mode, a task identifier matching multiple subtasks (e.g. `website_extraction` matching both `pass_a` and `pass_b`) raises `LLMNotConfiguredError` with `AMBIGUOUS_TASK_FILTER`.
5. **Exact Single Path Required:** Live campaigns strictly require the explicit canonical path `website_extraction:pass_a`.
6. **Preservation of Legitimate All-Task Mode:** In offline dry-run mode, passing `task_filter="all"` or `None` continues to evaluate all 7 canonical paths.

## 3. Phase 2 — Corrected Denominator Accounting & Scorecard Isolation

### 3.1 Disentangling Denominators
In prior versions, `CandidateTaskSummary` used `total = len(fixtures)` for all metrics, which conflated unattempted cases and transport dropouts with model quality failures.

We separated and explicitly persist:
- `cases_planned`: Total fixtures scheduled for the run (e.g., 10).
- `requests_attempted`: Cases dispatched to the gateway before hitting request caps.
- `responses_received`: Responses returned by the gateway.
- `cases_evaluable`: Responses successfully parsed without transport failures or uncertain timeout dropouts.
- `cases_passed`: Cases satisfying schema, ground-truth, evidence grounding, and safety rules.
- `transport_failures`: Failures caused by network, gateway dispatch, or request timeouts.
- `rate_limit_failures`: Failures specifically caused by HTTP 429 rate limiting.
- `unattempted_cases`: Planned cases aborted before dispatch due to request or budget caps.

### 3.2 The Critical Incomplete Run Invariant
**Eight successful responses out of ten planned fixtures must never qualify a candidate when two cases were unattempted or failed transport.**
- The overall pass rate is computed strictly against `cases_planned`:
  $$\text{overall\_pass\_rate} = \frac{\text{cases\_passed}}{\text{cases\_planned}}$$
- Qualification requires:
  1. `cases_evaluable >= 10` (true evaluation, not catalog presence).
  2. `cases_evaluable == cases_planned` (zero unattempted or transport-failed cases).
  3. `overall_pass_rate >= 0.80`.
  4. `safety_violations_count == 0`.

## 4. Phase 3 — Separation of Qualification from Production Approval

We established distinct, non-overlapping statuses across the evaluation lifecycle:

1. **Task-Level Evaluation Eligibility (`is_smoke_only: bool`):**
   - True if `cases_planned < 10` or `is_connectivity_smoke=True`.
   - Cannot qualify or approve candidate (`SMOKE_ONLY`).
2. **Task-Level Qualification (`task_qualification_eligible: bool`):**
   - True only when 10 planned cases are genuinely evaluated, `overall_pass_rate >= 80%`, and 0 safety violations occur.
3. **Multi-Task Model Qualification:**
   - Evaluated across all 7 Gateway task paths (70 cases). Passing `website_extraction:pass_a` alone does NOT establish whole-model qualification.
4. **Production Routing Authorization (`production_approval_state: str`):**
   - Initialized to `"NOT_APPROVED_PROPOSAL_ONLY"`.
   - Automated benchmark runs never promote or approve models for production routing.
   - **Sample Size Limitation:** Ten test cases constitute an engineering screening batch, not strong statistical evidence of production reliability.

## 5. Phase 4 — Inter-Request Delay Pacing

### 5.1 Architecture & Implementation
To prevent bursting free-tier rate limits (such as Gemini 15 RPM or Cohere 20 RPM), `ExternalBenchmarkRunner` now supports controlled pacing:
- Parameter `inter_request_delay_seconds: float = 0.0` (validated $\in [0.0, 10.0]$).
- Injected `sleeper: Callable[[float], None]` defaults to `time.sleep`, allowing deterministic and fast unit testing.
- Sleep is applied between completed dispatch attempts (including failed attempts), but skipped after the final case.
- Single-request smoke tests and default runners keep `inter_request_delay_seconds = 0.0`.
